# regional-authority-lab

Companion lab for **Article 3 — Active-Active Without Split-Brain**.

```bash
make verify
```

23 tests, no cloud project, no credentials, no network.

## What this lab is for

It demonstrates two things that sound contradictory and are not:

1. **The database cannot produce two truths.** Under partition, regional loss,
   and the same operation submitted in both regions at once, `doubleCommits` is
   zero in every scenario under every policy. That is a property of the
   majority quorum, not of the scenarios chosen — see below.
2. **The application absolutely can.** Under the identical faults, with the
   identical impeccable database, an application that decides from regional
   state tells the customer "yes" twice for one operation, and fires external
   side effects with nothing behind them.

Article 3's argument is that solving the first does not solve the second, and
that most "active-active" risk lives in the second.

## Why the safety claim is structural

`T2` enumerates every majority subset of the five voting replicas and asserts
that all pairs intersect. Because any two majorities share a member, a side
that can commit necessarily contains a replica that saw every prior commit.
`doubleCommits` is therefore empty for reasons independent of which scenarios
were run.

Negative control `N2` removes the majority requirement and shows both sides of
a partition accepting the same operation, which is what proves the rule is
doing the work.

## The topology modelled

The documented base multi-region shape: two read-write regions with two
read-write replicas each, plus a witness replica in a third region. Five voting
replicas, majority of three.

| Region | Voting replicas | Can form a quorum alone? |
|---|---:|---|
| `us-east` (default leader) | 2 | No |
| `us-west` | 2 | No |
| `witness` | 1 | No |
| `us-west` + `witness` | 3 | Yes |
| `us-east` + `us-west` | 4 | Yes |

## Headline result

From `results/experiments.md`. Simulated results.

Same partition, same database, two application policies:

| App policy | Told customer yes without confirmation | Side effects with nothing behind them | Database double-commits |
|---|---:|---:|---:|
| Authority-only | 0 | 0 | 0 |
| Local state | 2 | 2 | 0 |

## What this lab is not

**It is not Spanner.** It implements the documented majority-quorum rule and
nothing else. It does not model TrueTime, commit wait, split boundaries,
schema, or performance. It cannot tell you how Spanner behaves in any respect
the documentation does not state.

**It is not a benchmark.** Write costs are expressed as cross-region round
trips, not milliseconds, because quoting milliseconds for a region pair this
lab never contacted would be invention.

**There is no emulator mode.** The Spanner emulator does not model multi-region
replication or leader election, so it cannot demonstrate the property under
test.

## Layout

```text
src/
  quorum.ts      the majority rule, the intersection proof, the durable log
  simulator.ts   partitions, regional loss, leader election, app decisions
  scenarios.ts   the two application policies and the fault shapes
  latency.ts     write and read cost in round trips
tests/
  quorum.test.ts           T1-T9,  the quorum in isolation
  invariants.test.ts       T10-T18, properties across whole scenarios
  negative-control.test.ts N1-N5,  remove a mechanism, break a property
docs/adr/        three decision records
results/         generated by `make report`; never edited by hand
```

## Two modelling defects this harness caught in itself

1. **Double-commits were miscounted.** The counter incremented per *attempt*
   that had a durable outcome rather than per *accepted write*, so a correctly
   converging duplicate was reported as a violation. Fixed to count COMMITTED
   results.
2. **Divergence was defined too loosely.** Counting "one region fulfilled,
   another entered safe mode" as divergence flattered the unsafe policy, by
   making correct behaviour look like a failure too. Replaced with two honest
   measures: unbacked fulfilments in hindsight, and unconfirmed fulfilments at
   the moment the application answered.
