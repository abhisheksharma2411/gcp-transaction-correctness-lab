# durable-money-state-machine results

Generated by `scripts/report.ts`. Deterministic: no cloud project, no
credentials, no network.

## Where the crash lands

One payout, one transition that moves money, and a process that dies at
each point of that transition in turn. After the crash a second worker
inherits the entity, the unacknowledged task is redelivered, and the
deadline runs.

| crash point | state recorded | recovery | final state | provider submissions |
|---|---|---|---|---:|
| `none` | SUBMITTED | RECOVERED | **SETTLED** | **1** |
| `before-commit` | AUTHORIZED | RECOVERED | **SETTLED** | **1** |
| `after-commit-before-actions` | SUBMITTED | RECOVERED | **MANUAL_REVIEW** | **0** |
| `after-actions-before-ack` | SUBMITTED | RECOVERED | **SETTLED** | **1** |

Every row submits once. The row to read twice is
`after-commit-before-actions`: the payout records a submission that never
happened, and the only thing that discovers it is the deadline.

## Where the answer lives

The same lifecycle, run on two drivers executing the same transition
table. Then the orchestrator's execution-retention window passes, and
both are asked the same question: what is the state of this payout?

| driver | during the run | after the retention window |
|---|---|---|
| application-owned row | SUBMITTED | SUBMITTED |
| orchestration execution | SUBMITTED | **no answer** |

Retention modelled at 90 days; 1 execution(s) aged out.
