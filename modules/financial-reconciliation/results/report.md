# financial-reconciliation results

Generated by `scripts/report.ts`. Deterministic: no cloud project, no
credentials, no network. Wall-clock timings are printed to the terminal and
kept out of this file, because a number that changes between two runs of the
same experiment is not a result.

numbers about one stream. A dashboard that reports the first is compatible

## The lateness window against the correction window

The same evidence, replayed at six settings of the pipeline's allowed
lateness, against a correction deadline of 5 d.

| allowed lateness | dropped | accepted effects | matched | unmatched | exception | digest |
|---|---:|---:|---:|---:|---:|---|
| 1 h | 318 | 503 | 156 | 164 | 16 | `3c233ed4d3730cfd4d9c9bca` |
| 6 h | 27 | 779 | 352 | 22 | 26 | `9f07b8f9ce453561ed4e7e0d` |
| 1 d | 22 | 784 | 352 | 22 | 26 | `e1f4dd55d007cb32a574f019` |
| 2 d | 17 | 789 | 352 | 22 | 26 | `39da274fa7105087837afa02` |
| 5 d | 0 | 806 | 352 | 22 | 26 | `3e0d263984a9a2d642937212` |
| 7 d | 0 | 806 | 352 | 22 | 26 | `3e0d263984a9a2d642937212` |

At six hours, 27 records are dropped and the accepted effect
count falls from 806 to 779. The case-state summary is
**identical**: {"EXCEPTION":26,"MATCHED":352,"UNMATCHED":22}. The ledger balances in both.

That is the result this module exists to produce. A configuration that is
wrong by a factor of twenty loses evidence without changing a single number
on a reconciliation dashboard, and a balanced ledger does not notice.

## Recovery from the raw evidence

The same raw objects, read a second time by a pipeline whose window is wide
enough for the correction deadline.

| run | allowed lateness | dropped | accepted effects | digest |
|---|---|---:|---:|---|
| narrow | 6 h | 27 | 779 | `9f07b8f9ce453561ed4e7e0d` |
| re-read | 7 d | 0 | 806 | `3e0d263984a9a2d642937212` |
| baseline | 7 d | 0 | 806 | `3e0d263984a9a2d642937212` |

The re-read digest matches the baseline.
Nothing was recovered from the stream, because the stream no longer has it.
It was recovered from object storage, which is the only reason a lateness
window is a tuning parameter rather than a loss.

## Replay into a ledger that already exists

Every derived store is discarded and rebuilt by replaying the raw evidence
into the ledger that is already there.

| measured | before | after |
|---|---:|---:|
| accepted financial effects | 806 | 806 |
| derivations performed | 852 | 1704 |

Result digest before: `3e0d263984a9a2d642937212`, after: `3e0d263984a9a2d642937212` (unchanged).

Replaying the same evidence repeated the computation and did not create an
additional accepted financial effect. The replay cost is reported as work
done rather than as elapsed time, so that this file stays byte-identical
between runs.

## Negative controls

A corpus written by the same hand as the implementation proves nothing until
each case has been shown to fail when the mechanism it covers is removed.

| mechanism removed | cases that turn red | localised |
|---|---|---|
| `noDeliveryDedup` | R02 | yes |
| `noRawImmutability` | R18 | yes |
| `noStatementDedup` | R03, R04, R09 | yes |
| `naiveIdentity` | R04 | yes |
| `noCorrelation` | R05, R06 | yes |
| `noEntryDedup` | R10 | yes |
| `noFinalityGate` | R12 | yes |
| `postEverythingTwice` (blunt control) | 20 of 21 | **rejected** |

The blunt control is rejected rather than reported as a success. A mutation
that reddens the whole corpus cannot show which case covers which mechanism,
and `everything broke` is not evidence that anything in particular works.

One result here is uncomfortable and is left in. Removing delivery-level
de-duplication reddens exactly one case, and it reddens it on attribution
rather than on money: the assertion-level check underneath catches the same
duplicates. The raw store's create-if-absent precondition is buying work
avoided and the ability to detect an upstream system reusing an identity.
It is not buying financial correctness, and the controls say so.
